いま作っているツールは、まとめて QRX と呼んでいます。この記事では、QRX で何が必要で、どう考えて今の構成にしているかを書いておきます。

## 全体像

![QRX の全体像](./map.svg "図1　QRX の全体像。部品を、どう動くかで分けています")

QRX の部品は、どう動くかで 5 つに分けています。

- 常に動いているサービス：画面、API、市場の監視、データベース、ローカル LLM サーバー
- 必要なときに動かすコマンド：ニュースの要約や、このブログの公開前のチェック
- ライブラリ（関数群）：計算やデータの処理。サービスやコマンドから呼ばれて動きます
- デスクトップアプリ
- 置き場所：レポート

中心は qrxarts というリポジトリで、サービスとコマンド、ライブラリはここにあります。主に Python で書いていて、計算の重い部分だけ Rust で書いています。

QRX でやっていることは、大きく分けると次の 5 つです。

- 調べた結果を、画面で見られるようにする
- 市場をリアルタイムで見る
- 最適化やバックテストなどの計算をする
- 計算に使うデータを扱う
- レポートを書き出す。ニュースの要約などには、手元の LLM を使う

## 構成の考え方

### 計算はライブラリに置く

計算やデータの処理は、ライブラリの側に置いています。サービスやコマンドは、ライブラリを呼ぶだけにしています。

画面の Atlas は、API の Athena を呼びます。Athena は FastAPI で作っていて、データベースを読み書きしたり、ライブラリを呼んだりします。分析内容のアーカイブの Clio もライブラリで、それだけでは動かず、Athena の中で使われます。Jupyter からも同じ Athena を呼ぶので、画面と同じ計算をそのまま使えます。

### 計算の中心では、データを読み書きしない

最適化エンジンの Arts は関数型で書いています。計算の中心になる部分ではデータの読み書きをせず、同じ入力からはいつも同じ結果が出るようにしています。データを読む部分と、結果を書き出す部分は外側に分けています。

Metis も同じ考え方で、渡された表からバリュエーション用の Excel ワークブックを作るだけで、データを取りには行きません。

### 重い計算は Rust で書く

Arts の中でも、バックテストのように計算の重い部分は Rust で書いて、Python から呼んでいます。

### エンジンを差し替えられるようにする

ニュースの要約やレポートの作成には、手元の GPU で動かしているローカル LLM を使っています。このローカル LLM サーバーを Ares と呼んでいます。Ares の中で動かす推論エンジンは Strata、vLLM、Ollama から選べて、どれも OpenAI 互換の API で呼べるので、エンジンを変えても qrxarts 側のコードは同じです。

### 公開する前に、機械で確かめる

このブログはリポジトリごと公開しているので、下書きもコミットの履歴も誰でも読めます。そこで、コミットや push の前に、公開してはいけないものが入っていないかを Argus というコマンドで確かめています。Argus は Git の仕組みを使って、コミットや push のたびに自動で動きます。

### 単独で使えるものは、別のリポジトリにする

Ares、Theia、Lethe は、qrxarts とは別のリポジトリにしています。qrxarts がなくても使えるので、それぞれ単独で公開できます。

### できあがったものは、コードと分けて置く

レポートは LaTeX と PDF で、コードとは別の qrxreports というリポジトリに置いています。
